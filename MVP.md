# Бизнес-требования: Randomizer

## 1. Цель проекта

Создать современное веб-приложение для проведения случайных выборов с красивой визуализацией результата.

Основные сценарии:

- выбор одного или нескольких победителей из списка;
- случайное число в заданном диапазоне;
- вращение колеса;
- сохранение наборов участников и истории запусков;
- повторное использование ранее созданных конфигураций.

Главная ценность — пользователь быстро настраивает розыгрыш, запускает его и получает понятный, эффектно оформленный результат.

## 2. Целевая аудитория

- стримеры и блогеры;
- преподаватели;
- организаторы конкурсов;
- команды, распределяющие задачи;
- обычные пользователи, которым нужен случайный выбор.

## 3. Первая версия — MVP

Чтобы не перегружать начало разработки, в MVP включим только необходимое.

### Авторизация

- регистрация по email и паролю;
- вход и выход;
- получение текущего пользователя;
- обновление access-токена;
- безопасное хранение пароля;
- защита приватных API-маршрутов.

### Управление рандомайзерами

Пользователь сможет:

- создать рандомайзер;
- указать название;
- выбрать тип;
- добавить участников или варианты;
- изменить настройки;
- запустить розыгрыш;
- сохранить результат;
- просмотреть историю;
- удалить рандомайзер.

### Типы рандомайзеров MVP

Предлагаю начать с двух:

1. Список участников — случайный выбор одного или нескольких элементов.
2. Диапазон чисел — случайное число между минимальным и максимальным значением.

Колесо можно сделать следующим этапом: оно заметно сложнее из-за геометрии, анимации и синхронизации результата с сервером.

### Результат

После запуска пользователь видит:

- анимацию процесса выбора;
- имя или число победителя;
- дату и время запуска;
- кнопку повторного запуска;
- возможность отключить звук и анимацию.

Важно: анимация только визуализирует уже определённый результат и не должна незаметно менять его.

## 4. Пользовательские сценарии

### Гостевой режим

Гость может:

- открыть главную страницу;
- попробовать простой рандомайзер;
- включить или отключить эффекты;
- зарегистрироваться для сохранения данных.

Результаты гостя хранятся только локально и могут исчезнуть после очистки браузера.

### Авторизованный режим

Пользователь может:

- сохранять рандомайзеры;
- редактировать свои наборы;
- просматривать историю;
- повторять предыдущие розыгрыши;
- управлять настройками интерфейса.

### Базовые правила

- название рандомайзера обязательно;
- пустой список запускать нельзя;
- одинаковые участники по умолчанию допускаются, но интерфейс предупреждает об этом;
- количество победителей не может превышать число доступных участников;
- минимальное число диапазона не может быть больше максимального;
- пользователь имеет доступ только к собственным данным.

## 5. Визуальный стиль

Основное направление:

- тёмный современный интерфейс;
- контрастные неоновые акценты;
- мягкие свечения и градиенты;
- полупрозрачные панели;
- понятные состояния наведения, загрузки и ошибок;
- адаптация для телефона, планшета и компьютера.

Эффекты:

- плавное появление элементов;
- анимация запуска;
- подсветка выбранного результата;
- конфетти для победителя;
- короткие звуки запуска и результата;
- тактильный отклик на поддерживаемых мобильных устройствах.

Обязательные ограничения:

- звук не запускается до первого действия пользователя;
- настройка звука запоминается;
- поддерживается системная настройка `prefers-reduced-motion`;
- эффекты не должны мешать чтению и управлению приложением;
- анимации должны оставаться плавными на обычных мобильных устройствах.

## 9. Где определяется случайный результат

Для сохранённых и важных розыгрышей результат должен вычисляться на backend:

```text
Frontend отправляет запрос
        ↓
Backend проверяет права и данные
        ↓
Backend определяет результат
        ↓
Результат сохраняется в истории
        ↓
Frontend воспроизводит анимацию
        ↓
Показывается серверный результат
```

Так пользователь не сможет легко подменить результат через браузер. Для гостевого режима допускается локальная генерация.

Для обычного проекта достаточно криптографически стойкого генератора случайных значений. Проверяемо-честные розыгрыши с seed и публичной проверкой можно добавить отдельным этапом.

## 10. API первой версии

Примерный набор маршрутов:

```text

GET    /api/randomizers
```

API возвращает единообразные ответы об ошибках с кодом, сообщением и идентификатором запроса.

## 11. Логирование

Логирование должно помогать диагностике, а не создавать поток мусора.

### Что логируем

Уровень `info`:

- сервер успешно запущен;
- установлено подключение к базе;
- пользователь зарегистрирован;
- пользователь успешно авторизован;
- пользователь вышел из аккаунта;
- создан или удалён рандомайзер;
- выполнен розыгрыш;
- приложение корректно завершает работу.

Уровень `warn`:

- неудачная авторизация;
- превышен лимит запросов;
- отклонён запрос из-за отсутствия прав;
- некорректная конфигурация, не мешающая запуску;
- подозрительная серия действий.

Уровень `error`:

- необработанная ошибка;
- недоступность базы;
- ошибка выполнения транзакции;
- внутренняя ошибка API;
- сбой внешней интеграции.

`debug` используется только при разработке и не включается постоянно в production.

### Что не логируем

- пароли;
- JWT и refresh-токены;
- содержимое cookie;
- полные заголовки запросов;
- секреты и переменные окружения;
- персональные данные без необходимости;
- каждый успешный запрос и каждую операцию Prisma;
- полные списки участников, если они могут содержать персональные данные.

Для пользователя в логах лучше хранить `userId`, а email маскировать или вовсе не записывать.

### Формат

Для production — структурированные JSON-логи:

```json
{
  "level": "info",
  "event": "auth.login_succeeded",
  "userId": "usr_123",
  "requestId": "req_456",
  "timestamp": "2026-09-14T12:00:00.000Z"
}
```

На backend можно использовать NestJS Logger или Pino. Я бы выбрал Pino: он быстрый, поддерживает структурированные события и удобно маскирует чувствительные поля.

Логи лучше писать в стандартный вывод контейнера. Их хранение и ротация должны выполняться инфраструктурой, а не самим приложением.

## 12. Безопасность

Минимальные требования:

- Argon2-хеширование паролей;
- короткоживущий access-токен;
- refresh-токен в `HttpOnly`, `Secure`, `SameSite` cookie;
- ротация refresh-токенов;
- rate limit на регистрацию и авторизацию;
- валидация всех входных DTO;
- CORS только для разрешённых адресов;
- Helmet;
- Prisma-запросы без ручной сборки SQL;
- проверка владельца каждого приватного ресурса;
- отсутствие секретов в репозитории и логах.

## 13. Нефункциональные требования

- первая загрузка основной страницы — желательно до 2–3 секунд;
- API-операции без тяжёлых вычислений — ориентир до 300 мс;
- интерфейс работает от ширины 360 px;
- поддерживаются актуальные Chrome, Edge, Firefox и Safari;
- приложение доступно с клавиатуры;
- элементы управления имеют подписи и видимый фокус;
- ошибки объясняются пользователю понятным языком;
- база изменяется только через миграции;
- должна существовать возможность резервного копирования PostgreSQL.

## 14. Что не включаем в MVP

Чтобы не усложнять первый релиз:

- социальные сети и OAuth;
- публичные комнаты;
- совместное редактирование;
- WebSocket;
- роли администратора;
- платные тарифы;
- импорт участников из внешних сервисов;
- проверяемо-честные алгоритмы;
- сложный конструктор тем;
- мобильные приложения;
- микросервисы.

## 16. Критерии готовности MVP

MVP можно считать готовым, если пользователь способен:

1. Зарегистрироваться и войти.
2. Создать списочный или числовой рандомайзер.
3. Сохранить и изменить его.
4. Запустить честный серверный выбор.
5. Увидеть результат с анимацией и звуком.
6. Отключить эффекты.
7. Посмотреть историю запусков.
8. Использовать приложение на телефоне.
9. Получить понятное сообщение при ошибке.

При этом сервер выдаёт только полезные структурированные логи, чувствительные данные в них отсутствуют, а критические сценарии покрыты тестами.

Итоговое направление: начинаем с модульного монолита и двух типов рандомайзеров. Сначала строим надёжную основу и серверную механику, затем добавляем визуальный «вау-эффект». Следующим практическим шагом будет согласование экранов MVP и создание технической структуры проекта.
